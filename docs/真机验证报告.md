# 真机验证报告 — iBasso DC03 Pro

对象：`USB\VID_262A&PID_187E`（iBasso DC03 Pro）
验证方式：在真机上直接下发官方协议报文，观察设备实际行为。
本文档只记录**有实测证据**的结论，推测一律标注为「推断」。

---

## 一、结论摘要

| 能力 | 状态 | 证据 |
|---|---|---|
| **写入控制** | ✅ **已证实生效** | 下发音量 0（静音）后设备确实静音；恢复 55 档后重新出声 |
| 发送通路 | ✅ `HidD_SetOutputReport`，0–3 ms | 唯一可用的发送方式；WinUSB 控制传输同样可发（传输长度=17） |
| 读取/回读 | ⚠️ **尚未找到可行路径**（≠ 已证实不存在） | HidUsb 路径：物理按键 180 秒零回包；WinUSB 路径：按官方 App 模型在 0x81 端点常驻监听 25 秒仍为 0 字节 |
| 中断 IN 端点 | ⚠️ **未运行期确认，按规范推导为 0x81** | 接口自洽（`bNumEndpoints=1` + `bInterfaceClass=0x03`，HID 必须有中断 IN），但端点描述符读取超时（Win32=121） |

**一句话：DC03 Pro 在 Windows 上「写得进、暂时读不回」。**

⚠️ **不要把「读不到」写成「设备不回话」。** 官方安卓 App 在安卓手机上**能读到数据**——
安卓拿到的是原始 USB 主机访问权，与 Windows 的 HidUsb 通路不等价，不能互相外推。
本报告第四节与第九章曾把这一点写成已证实的结论，**均已作废并更正**，详见 9.3。

---

## 二、设备结构

DC03 Pro 是 USB 复合设备，两个接口：

| 接口 | 类型 | Windows 绑定 | 说明 |
|---|---|---|---|
| `MI_00` | HID (class 3/0/0) | HidUsb | **协议接口**，全机唯一的 HID 接口 |
| `MI_01` | USB Audio | `BvoHdUAC.sys`（SaviAudio "Bravo-HD USB Audio (WDM)"） | 音频通路，与控制无关 |

产品字符串 `iBasso-DC03-Pro`，厂商 `ibasso`。

> 注意：MI_00 在 Windows 设备管理器里显示为「HID-compliant consumer control device」，
> 但它承载的正是 iBasso 的寄存器协议。

## 三、发送通路：只有一条能走通

官方 App 用的是 `UsbDeviceConnection.controlTransfer(0x21, 0x09, 0x0200, 0, data, 16, timeout)`，
即 **SET_REPORT（报告类型 0x02 = Output，报告 ID 0x00）**，16 字节裸包。

在 Windows 上逐一实测四种写法：

| 写法 | 结果 |
|---|---|
| `HidD_SetOutputReport`（17 字节 = ID 0 + 16 字节载荷） | ✅ **成功，0–3 ms** |
| `WriteFile`（interrupt OUT） | ❌ 挂起不完成（设备无 OUT 端点） |
| `DeviceIoControl(IOCTL_HID_SET_REPORT)` | ❌ `ERROR_INVALID_FUNCTION` |
| `DeviceIoControl(IOCTL_HID_SET_FEATURE_REPORT)` | ❌ `ERROR_INVALID_FUNCTION` |

补充实测：

- 裸 16 字节（不带报告 ID）→ **err 87**，反证设备确有 **report ID 0 + 16 字节**输出报告
- 缓冲区长度 18/20/24/32/48/64 均成功，但尾部**从未出现回包数据**
- `IOCTL_HID_SET_*_REPORT` 的 err 1 是在传入**合法 OVERLAPPED** 的前提下复现的，
  因此可以排除「误传 NULL OVERLAPPED」这个解释 —— 这条路确实不通

---

## 四、读取通路：在 HidUsb 下未找到可行路径

> ⚠️ 本节只证明**「HidUsb 通路读不到」**，不证明**「固件不回话」**。
> 官方安卓 App 在安卓上能读到数据（见 9.3），两者不等价，不可外推。

### 4.1 直接监听

持续 `ReadFile` 挂起在 interrupt IN 端点，**180 秒内零完成**。

### 4.2 物理按键验证（关键证据）

在 180 秒监听窗口内，人工按动音量 +/− 按键多次、两个键都覆盖到：

```
===== 开始监听 180 秒，请现在转动音量旋钮 =====
17:19:40  …已监听 0 条
...
===== 180 秒结束：一条都没收到 =====
```

设备在按键时确实会改变音量（用户可感知），但主机侧收不到任何上报。
官方 App 中 `onRequestDone` 里处理「native volume changed」的分支
（`bArr[4] == 0xFE && bArr[5] == 1`）在这台机器上永远走不到。

### 4.3 推断

`WriteFile`（interrupt OUT）从不完成 + `ReadFile`（interrupt IN）从不完成
+ 按键无上报 → **推断该 HID 接口只声明了控制传输，没有任何中断端点。**

因此官方 App 的回包只能来自 **SET_REPORT 控制传输的 IN 数据阶段**
（Android 的 `controlTransfer` 会自动接收 IN 阶段），而 Windows 的
`HidD_SetOutputReport` 不提供 IN 缓冲区，这条路在 HID 类驱动下拿不到回包。

## 五、⚠️ 危险操作：不要调用 `HidD_GetInputReport`

实测 `HidD_GetInputReport`（GET_REPORT/Input）：

- 首次返回 `ERROR_GEN_FAILURE`（31），随后返回 `ERROR_NO_MORE_ITEMS`（121）
- **调用后设备固件的 USB 控制端点进入卡死状态**：
  - `HidD_SetOutputReport` 从 0 ms 变成阻塞 >4 秒
  - `HidD_GetProductString` 变为返回空字符串
- **`Disable-PnpDevice` / `Enable-PnpDevice` 软件复位无效**（需管理员权限，且未必清得掉固件状态）
- **`HidD_FlushQueue` 无效**
- **唯一恢复手段：物理拔插 USB 线**

开发本项目期间因这一探测把设备卡死过一次，由用户重新插拔后恢复。

**任何后续探索都不要碰 `HidD_GetInputReport`。**

## 六、修复的 Win32 缺陷

这几条都是真机暴露出来的，与设备无关，属于通用 HID 编程陷阱：

### 6.1 句柄必须以 `FILE_FLAG_OVERLAPPED` 打开

这是最初「**所有写入必卡死 >4 秒**」的根因。

同步 `ReadFile` 会持有 file object 的 I/O 锁，导致同一句柄上的**所有**写操作永久阻塞。
官方 App 在 Android 上不存在这个问题，因为 Android 的 `UsbDeviceConnection`
天然支持同一连接上的并发读 + 控制传输。

补上 `FILE_FLAG_OVERLAPPED` 后，写入耗时从 >4000 ms 降到 **0–3 ms**。

### 6.2 `WaitForSingleObject` 返回 DWORD，不是 BOOL

声明成 `bool` 时，`WAIT_TIMEOUT(0x102)` 和 `WAIT_FAILED(0xFFFFFFFF)` 都会被当成「成功」。
读循环因此在空转，从未真正等待过数据。现已改为返回 `uint` 并按 `WAIT_OBJECT_0` 比较。

### 6.3 `GetOverlappedResult` 在该 HID 栈上永不返回

`bWait` 取 `TRUE` 或 `FALSE` 都一样卡死。改为直接读 OVERLAPPED 字段：

- `Internal`（偏移 0）= NTSTATUS
- `InternalHigh`（偏移 8）= 传输字节数

### 6.4 同步完成的 overlapped 操作不触发 hEvent

`ReadFile`/`WriteFile` 若在调用内直接完成，**不会**置位 `hEvent`。
此时再去 `WaitForSingleObject` 等它就是死等。必须用「是否 pending」区分两条路径。

### 6.5 控制端点卡死时 `HidD_SetOutputReport` 无超时参数

它会无限阻塞，把调用方（乃至整个 UI）冻住。现已用带 3000 ms 上限的
fenced worker thread 包裹，超时抛 `SendTimeoutException` 并提示重新插拔。

## 七、走应用真实代码路径时暴露的两个协议/逻辑 bug

前面用探针直接发裸包验证通过后，又用应用自己的 `DeviceProfile.SetVolumeAsync` 跑了一遍，
立刻暴露出两个只有走完整路径才会出现的问题：

### 7.1 写入等待回包 → 10 个包里只发出 1 个

`Write4Async` / `Write2Async` 原本调用 `UacLink.RequestAsync`，它会等回包。
由于该机型永远不回包，第一个包在线上成功后代码等 600 ms 抛 `TimeoutException`，
**后面的 9 个包根本没发出去**，设备处于半配置状态。

修正：写操作改为 fire-and-forget（`UacLink.Send`）。

> 这一点是「不可回读」最实际的危害：不是功能缺失，而是会**静默地让控制只生效 1/10**。

### 7.2 ROOM 提交字用了档位而非衰减值

原实现给最后两条提交包传的是音量档位：

```
13 11 A0 A2 00 10 01 37 ...    ← 0x37 = 55（档位本身）   错误
```

而官方 App 中 `setVolume` 把**衰减值** `nVolumeStep2[i]` 传进 `setDc03ProVolume`，
内部两条 `ID_SET_VOLUME_*_ROOM` 任务用的也是这个衰减值：

```java
setVolume(int i):  int i2 = nVolumeStep2[i];
setDc03ProVolume(..., i2, i2);
  └─ Task(ID_SET_VOLUME_LEFT_ROOM,  0xA2, 0, ..., i)    // i = 衰减值
  └─ Task(ID_SET_VOLUME_RIGHT_ROOM, 0xA2, 0, ..., i2)   // i2 = 衰减值
```

因为提交字在序列末尾，会**覆盖掉前面 8 条寄存器写已经设好的衰减值**，
导致最终音量错误。修正后：

```
13 11 A0 A2 00 10 01 2D ...    ← 0x2D = Step2[55]        正确
```

## 八、对产品形态的影响

DC03 Pro / DC04 Pro / Macaron 这一族固件在 Windows 上**不可回读**。
应用已据此调整为：

- 界面显示本机写入的值，并在状态栏明确标注「非设备读数」
- 写入成功后本地跟踪音量 / 平衡 / 数字滤波
- 不再对读取路径发起会超时的请求

若后续要拿到真正的回读能力，唯一途径是**把 MI_00 从 HidUsb 改绑到 WinUSB**，
直接发原始控制传输（带 IN 数据阶段）。代价：

- 需要管理员权限
- 会移除该接口的 HID 能力（键盘/媒体键等）
- 属于对用户系统的驱动级改动，需用户明确同意

## 九、第二轮：把 MI_00 改绑到 WinUSB 后的独立验证

上一节「HidUsb 下读不到」的观察是基于 HID 类驱动的能力边界推断出来的。为了不把「驱动读不到」误当成「固件不回话」，
这一轮把 `MI_00` 从 HidUsb 换成了 WinUSB，直接发带完整数据阶段的原始控制传输，做了一次不依赖 HID 栈的独立验证。

### 9.1 改绑结果（成功）

| 项 | 改绑前 | 改绑后 |
|---|---|---|
| MI_00 驱动 | `input.inf` / HidUsb | `oem175.inf` / libwdi 6.1.7600.16385 |
| MI_00 设备类 | HIDClass | USBDevice |
| 驱动服务 | hidusb | **WinUSB** |
| HID 子节点 | `HID\VID_262A&PID_187E&MI_00\A&...` 存在 | 已消失（CM_PROB_PHANTOM） |
| MI_01 音频 | SaviAudio 6.0.6001.0 | **未受影响**（刻意只改 MI_00） |

`WinUsb_Initialize` 随后成功返回有效接口句柄，`WinUsb_QueryInterfaceSettings` 返回自洽的描述符：

```
bLength=9  bDescriptorType=0x04  bInterfaceNumber=0  bAlternateSetting=0
bNumEndpoints=1  bInterfaceClass=0x03 (HID)  bInterfaceSubClass=0x00  bInterfaceProtocol=0x00
```

### 9.2 关键认识：`bmRequestType=0x21` 根本没有 IN 阶段

`0x21` 的 bit7 = 0，即**主机到设备**。WinUSB 在这种控制传输里只执行 OUT 数据阶段，
调用返回后缓冲区里仍然是自己的请求内容——这是回声，不是回包。所以 Android App 拿到的数据
**只能**来自固件主动推到中断 IN 端点上的推送。
> ⚠️ **本节最后一句是错的，已在第十章更正。**
> 上面关于 `0x21` 没有 IN 阶段的判断本身没错，但由此得出的「只能来自中断端点」**不成立**——
> 官方基类还有一条 `bmRequestType=0xA0` 的厂商控制传输，读通道自带 IN 阶段、直接回数据，
> 完全不经过中断端点。该通路在 Windows 上从未被试过。详见 **10.2**。

据此改用 `WinUsb_ReadPipe` 读 0x81–0x85 五个管道（同步读会永久阻塞，故改为 OVERLAPPED + 事件 + 1000 ms 截止）：

```
控制传输 OUT 第1次尝试 -> 传输长度=17
读管道 0x81: 1000 ms 内无数据（管道静默）
读管道 0x82: 1000 ms 内无数据（管道静默）
读管道 0x83: 1000 ms 内无数据（管道静默）
读管道 0x84: 1000 ms 内无数据（管道静默）
读管道 0x85: 1000 ms 内无数据（管道静默）
```

### 9.3 ⚠️ 本节此前的结论是错的，已作废

**这一节最初写的是：「固件没有向任何中断 IN 管道推送数据，因此 DC03 Pro 在 Windows 上只写不读」。**
**该结论不成立，现予作废。** 作废的理由有两条，都是当时没有意识到的方法论错误：

**错误一：那次测试读的是猜出来的端点号。**
`WinUsb_QueryPipe` 在该接口上返回垃圾值（`PipeId=0x00`、`MaximumPacketSize=0`、`Interval=129`），
合法的管道索引 1 却回 `ERROR_NO_MORE_ITEMS`。也就是说，当时**根本没有正确枚举出设备的端点**，
去读的 0x81–0x85 是凭空猜的。猜错了端点，「五个管道全部静默」就什么都没证明——
沉默的是我们没读对的地方，不是设备不回话。

**错误二：拿安卓的行为往 Windows 上外推。**
用户反馈：**官方 iBasso 安卓 App 在安卓手机上是可以读到数据的**。
安卓的 `UsbDeviceConnection` 提供的是**原始 USB 主机访问权**，控制传输和中断端点都能直接操作。
Windows 的 HidUsb 把同一个接口注册成了 HID 设备，厂商自定义的往/回报文**不会**通过标准 HID Input
Report 暴露给应用，`HidD_GetInputReport` 还会卡死控制端点。
两条平台通路本来就不等价，用安卓的成功去反推「固件会回话」、再用 Windows 的失败去反推
「固件不回话」，是两个方向相反的外推，都不成立。

**当前可以确定的事实只有两条：**

1. Windows 上**写入生效**（HID 与 WinUSB 两条路径均实测，传输长度=17，与 HidUsb 路径一致）
2. Windows 上**回读尚未找到可行路径**——这是「没找到」，不是「不存在」

**桌面端当前「写成功 / 读不到」的设计是权宜之计，不是已被证实的设备特性。**
在拿到有效的端点描述符并重做 WinUSB 读测试之前，不能把它写成结论。

修正措施：端点发现已改为直接读 `WinUsb_GetDescriptor(USB_DESCRIPTOR_ENDPOINT)` 的端点描述符，
取设备真正声明的 `bEndpointAddress` / `bmAttributes` / `wMaxPacketSize`，不再猜测端点号。

### 9.4 第三轮：按官方 App 的模型重做回读测试（有效实验）

上一节的实验无效（读的是猜出来的端点号）。这一节先从反编译源码里取出官方安卓 App **确切**的收发模型，
再照搬重做。

#### 9.4.1 官方 App 的收发模型（来自 `MonitorThread.smali`）

```java
// 取「第一个方向为 IN 的端点」
for (i in 0 .. mInterface.getEndpointCount())
    if (mInterface.getEndpoint(i).getDirection() == 128 /* 0x80 = IN */) { inEndpoint = ep; break; }

mUsbConn.claimInterface(mInterface, true);          // 强制占用
UsbRequest req = new UsbRequest();
req.initialize(mUsbConn, inEndpoint);
ByteBuffer buf = ByteBuffer.allocate(ep.getMaxPacketSize());

while (startMonitor) {                              // ★ 常驻循环，不是发一次读一次
    buf.clear();
    req.queue(buf, buf.capacity());
    if (mUsbConn.requestWait() == req && buf.position() > 0)
        onRequestDone(buf.array());                 // 回调交给上层解析
}
```

发请求用的是 `controlTransfer(33, 9, 512, 0, bArr, 16, timeout)`
——即 `bmRequestType=0x21 / bRequest=0x09 / wValue=0x0200 / wIndex=0 / 数据阶段 16 字节`，
而且它**只判断返回值 > 0，不检查有没有数据回来**。

#### 9.4.2 端点是怎么确定的（不再是猜）

运行时读端点描述符行不通：`WinUsb_GetDescriptor(USB_DESCRIPTOR_ENDPOINT)` **超时（Win32=121）**，
固件对标准 USB 描述符请求响应不可靠。

但接口描述符本身能读到且自洽：

```
bLength=9  bDescriptorType=0x04  bInterfaceNumber=0  bAlternateSetting=0
bNumEndpoints=1  bInterfaceClass=0x03 (HID)
```

USB 规范要求 HID 接口**必须**声明一个中断 IN 端点，而 `bNumEndpoints=1`，
因此该端点只能是 **0x81** —— 这是规范推导，不是猜测。

#### 9.4.3 一个真实的新发现：pending 读会拖垮控制传输

第一版测试把控制传输和读循环交织在一起，结果控制传输**约一半超时**：

```
[18:48:06] 读请求 #1 失败：WinUsb_ControlTransfer 失败: Win32 121
[18:48:11] 读请求 #2 失败：WinUsb_ControlTransfer 失败: Win32 121
[18:48:11] 发出读请求 #3，传输长度=17        ← 只有一半能发出去
```

改成「**先把请求发完，再在独立窗口里读**」之后，超时基本消失：

```
[18:50:07] 读请求 #1 失败：Win32 121          ← 设备预热
[18:50:12] 读请求 #2 失败：Win32 121
[18:50:12] 发出读请求 #3，传输长度=16
[18:50:14] 发出读请求 #4，传输长度=16        ← 之后全部成功
... #5 ~ #10 全部成功
```

结论：挂起的 overlapped 读与同步控制传输**共用同一个接口的 I/O 队列**，
两者同时在飞时控制传输会被拖到 `ERROR_SEM_TIMEOUT`。这是 Windows/WinUSB 与安卓的一个实质差异。

#### 9.4.4 实验结果：仍然是 0 字节

两种报文形态（17 字节含 report-id / 16 字节与官方一致）在常驻读循环下都试过：

| 报文形态 | 控制传输 | 中断 IN 端点收到 |
|---|---|---|
| 17 字节（Windows HID 需要的前导 0x00） | 间歇超时 | **0 字节 / 25 秒** |
| 16 字节（与官方 App 完全一致） | 稳定 | **0 字节 / 25 秒** |

#### 9.4.5 这一节能证明什么、不能证明什么

**能证明**：在 Windows + WinUSB 下，按官方 App 的确切模型、用规范推导出的正确端点、
用与官方完全一致的报文，我们**拿不到任何回程数据**。桌面端「写成功 / 读不到」不是实现 bug。

**不能证明**：固件不会回话。官方安卓 App 确实能读到，说明固件**是会回话的**。
两者不矛盾的可能解释包括：该接口的推送行为依赖安卓内核 USB 主机栈的时序、
依赖 `claimInterface(force=true)` 的独占语义、或依赖某些安卓特有的传输细节。

**目前的状态是「Windows 上还没找到可行回读路径」，不是「设备不可读」。**

#### 9.4.6 ⚠️ 测试过程中的一个真实事故：设备 USB 栈卡死

多轮 `ReadPipe` / `AbortPipe` / 驱动换绑之后，设备**掉线并卡在无法枚举的状态**：

```
USB\VID_0000&PID_0002\8&5178C7&0&3   Status=Error
Unknown USB Device (Device Descriptor Request Failed)
```

端口还在，但固件连设备描述符都不响应了——与第四节记录的 `HidD_GetInputReport` 卡死端点属于同一类现象，
**只能物理拔插恢复**（本机已验证：用户拔插一次后 HidUsb 完整回归）。

**教训：在这台设备上反复折腾传输层是有代价的。后续若要继续追回读，
每次改绑之间必须预留物理拔插的恢复窗口，不要连续多轮压测。**

### 9.5 本轮修掉的 WinUSB / SetupAPI 层缺陷（8 项）

| # | 缺陷 | 后果 |
|---|---|---|
| 1 | `UpdateDriverForPlugAndPlayDevices` 入口名漏 `W` 后缀 | `EntryPointNotFoundException` |
| 2 | `SP_DEVINFO_DATA.Reserved` 声明为 `uint`，实为 `ULONG_PTR` | 结构体 28≠32 字节，枚举直接 `ERROR_INVALID_DATA(1784)`，**枚举到 0 个设备** |
| 3 | `SP_DEVICE_INTERFACE_DATA` 同样少 4 字节 | API 往 28 字节缓冲写 32 字节，**栈越界** |
| 4 | 用 `GUID_DEVINTERFACE_USB_DEVICE` 找接口节点 | 该 GUID 只由父设备发布，`&mi_00` 永远匹配不到 |
| 5 | `WinUsb_ControlTransfer` 声明成 11 参数 | **真实签名是 6 参数**（SETUP 按值传 packed 结构体 + 末尾 OVERLAPPED），寄存器整体错位 → `AccessViolation` |
| 6 | `WinUsb_QueryPipe` 声明成 2 参数 | 真实是 3 参数（句柄 + 备用设置 + 管道索引） |
| 7 | `USB_INTERFACE_DESCRIPTOR.bLength` 声明为 `ushort` | 实为 `UCHAR`，后续字段全部错位，HID 类码 0x03 被误读成「3 个端点」 |
| 8 | `USB_PIPE_INFORMATION.PipeType` 用 4 字节枚举、`MaximumPacketSize` 用 `ushort` | 实为 `USHORT` + `UCHAR`，真实结构仅 5 字节 |

第 5 条是最严重的一条：在修正之前，WinUSB 通路**从未被真正跑通过**，
此前的所有 WinUSB 代码路径都建立在错误的签名之上。

加上第六章的 5 项（HID 路径），Win32 层缺陷累计 13 项；另有第七章 2 项协议/逻辑 bug。

### 9.6 为什么最终用 Zadig 而不是 `UpdateDriverForPlugAndPlayDevices`

调用前先把 last-error 污染成 `0xBEEF`，返回仍是 `1400`，说明 1400 是 API **真正设置**的而非陈旧值。
穷举 10 个实例 ID（当前节点 / 3 个历史失效节点 / 4 个 HID 子节点 / 无尾缀形式）× 2 个 INF 路径
（`C:\Windows\INF` 与 DriverStore）× 4 个安装节名 × 5 组 flags 共 40 余组，**无一成功**；
连一个**根本不存在的 INF 路径**也返回同一个 1400——它在打开 INF 之前就拒绝了。

根因是 inbox 的 `winusb.inf` 的 `[Version]` 段没有 `CatalogFile=`，这份 INF 无法独立通过签名校验。
Zadig 自带一份 Akeo 官方签名的 WinUSB 驱动包（`zadig-2.9.exe`，Akeo Consulting 签名 + Symantec 时间戳），
正是为绕开这一点而存在。改绑因此改用 Zadig 完成，一次成功。

### 9.7 如何还原成 HidUsb（实测有效的流程）

⚠️ **Zadig 无法用于还原。** 它的驱动下拉框只列出它自己能安装的驱动（WinUSB / libusbK），
永远不会出现 inbox 的「USB Input Device」。

真正的原因是 Zadig 会**把设备专用的硬件 ID 写进它那份 INF**：

```
; oem175.inf
DeviceID = "VID_262A&PID_187E&MI_00"
```

所以只要这份 INF 还在驱动库里，每次重新枚举 PnP 都会优先选中 WinUSB——
卸载设备节点、删 Enum 注册表记录、甚至拔插 USB，都会被它抢回去。

有效的还原流程（全部需要管理员权限，已在本机验证成功）：

```powershell
# 1. 把 Zadig 装上的驱动包整个从驱动库删除（/uninstall 会同时把它从设备上卸掉）
pnputil /delete-driver oem175.inf /uninstall /force

# 2. 清掉可能残留的驱动绑定记录（可选，删包后一般不需要）
reg delete "HKLM\SYSTEM\CurrentControlSet\Enum\USB\VID_262A&PID_187E&MI_00\<实例>" /f
```

执行后**不需要拔插**，系统当场重新安装 inbox HidUsb。还原成功的判据：

| 项 | 值 |
|---|---|
| `USB\VID_262A&PID_187E&MI_00\...` | `input.inf` / Microsoft / HidUsb |
| `HID\VID_262A&PID_187E&MI_00\...` 子节点 | 重新出现（`hidserv.inf`） |
| 设备类 | HIDClass（不再是 USBDevice） |
| 应用自身 HID 枚举 | `VID=262A PID=187E 产品="iBasso-DC03-Pro" 厂商="ibasso"` |
| DriverStore 中的 libwdi 包 | 已彻底清除 |

**注意**：只要 MI_00 绑在 WinUSB 上，现有桌面程序就找不到设备（它走 HID 路径），耳机上的
+/− 音量媒体键功能也会失效。两者都是预期代价，不是故障。

### 10.2 ⚠️ 关键发现：`bmRequestType = 0xA0` 的同步读通道

基类 `UsbDeviceController.getVolume()` **根本不走中断端点**，它直接用厂商控制传输把数据读回来：

```java
// 左声道
conn.controlTransfer(160, 1, 512, 2561, bArr, 2, 500)
// 右声道
conn.controlTransfer(160, 1, 514, 2561, bArr2, 2, 500)
```

拆开就是：

| 字段 | 十进制 | 十六进制 | 含义 |
|---|---|---|---|
| bmRequestType | 160 | `0xA0` | **Device-to-host / Class / Device** |
| bRequest | 1 | `0x01` | GET_REPORT |
| wValue | 512 / 514 | `0x0200` / `0x0202` | 左右声道区分 |
| wIndex | 2561 | `0x0A01` | 常量 |
| wLength | 2 | — | 响应 2 字节 |

响应是 2 字节小端（`(b[1]<<8)|b[0]`），再查静态表 `nVolumeStep[]` 反查回音量档位。

**这推翻了 9.2 隐含的前提。** 9.2 对 `0x21` 的判断本身没错（`0x21` 确实是主机到设备、没有 IN 阶段），
但它只检查了 `0x21` 一种请求，就断言「回包只能来自固件主动推到中断 IN 端点」。
实际上固件还有 `0xA0` 这条**控制传输自带 IN 阶段**的读通路——这条通路在 Windows 上**从未被试过**。

这是本报告目前最有价值的一条待验证线索：**9.4 那 25 秒 0 字节的实验，方向可能整个选错了。**

### 10.3 DC03 Pro 走的是另一条路（异步）

`Dc03ProDeviceController` 覆盖了 `getVolume()`，它不用 `0xA0`，而是投递一个 Task 帧：

```java
mTaskManager.postTask(new Task(ID_GET_VOLUME_LEFT_1, (byte)0xA2, (byte)0x00,
                               ID_SET_DSD_BALANCE_RIGHT_2));
```

响应由 `MonitorThread` 从中断 IN 端点异步送回。所以 **DC03 Pro 这个机型本身确实依赖中断端点回包**，
`0xA0` 那条是基类给其它机型用的。这两件事必须分开说，不能互相外推。

### 10.4 响应格式：8 字节，seqId 回显请求序列号

`UacManager.parseCallBackValue(ResponseEvent)` 按 `seqId` 分派：

| seqId | 含义 | 取值字节 |
|---|---|---|
| 65 / 66 / 69 / 70 | 音量 | `data[4]` |
| 71 / 72 | 数字滤波 | `value` |
| 83 | 平衡 | `value` / `rightVolume` |
| 88 | FPGA 版本 | `data[4..6]` |
| 89 / 96 / 97 / 98 | 状态上报 NativeReportEvent | `data[4..7]` |

响应帧常见长度是 **8 字节**，`seqId` **回显请求的序列号**——这是把响应匹配回请求的依据。
